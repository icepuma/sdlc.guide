## Status and relationship rules

- **Draft or In review:** `Supersedes` and `Superseded by` are `None`. Use **Proposes to supersede** only to show review intent; it does not replace, deprecate, or change the authority of another record.
- **Accepted:** Set **Proposes to supersede** to `None`. This is the current decision. If it replaces an Accepted RFC predecessor, update both RFC records together: set this record’s **Supersedes**, then set the predecessor’s status to **Superseded** and its **Superseded by** field.
- **Rejected, Withdrawn, or Postponed:** Set **Proposes to supersede** to `None`. No normative supersession field is set. Retain any useful review history without presenting it as a replacement.
- **Superseded:** This Accepted historical decision was replaced by an Accepted RFC successor. Its **Superseded by** field must name that RFC.

Normative supersession is RFC-to-RFC only. An ADR needs an Accepted ADR successor. An RFC may link an ADR in **Related work** or **Decision outcome**, but must not set its normative relationship fields or change its status.

### Mandatory recipient semantic integrity

For every outbound HTTP effect, require before recipient lookup or effect either a verified non-transforming end-to-end semantic path, with no unverified TLS termination or rewrite between dispatcher and recipient of a fingerprint input, or authenticated coverage of every pinned recipient-fingerprint input. The coverage profile must name the HTTP method, required `https` scheme, canonical authority, verified recipient service identity and its verification source, intended tenant and its authenticated mapping, exact normalised resource, every allowlisted semantic header including the logical case-insensitive `idempotency-key` field, and the body or a named full-request or body digest. A resource alone is insufficient: canonical authority, verified recipient service identity, and intended tenant are separate required fingerprint inputs. The recipient must derive them from the actual request, connection, and configured service mapping, then verify their coverage, equality, and any named digest before lookup or effect. A trusted proxy is eligible for the non-transforming path only when it proves preservation of every fingerprint input; if it terminates TLS or rewrites authority, service identity, tenant, or resource, it must supply an authenticated assertion that the recipient independently verifies. Do not permit an optional or unauthenticated-digest path.

Pin the fingerprint's named collision-resistant algorithm, canonical byte form and component order, normalisation rules for scheme, authority, resource, tenant, and semantic headers, verified-service-identity source and mapping, body byte domain, output encoding, and version; persist its definition and expected value with the work. The recipient recomputes it from the actual received request and verified connection or proxy assertion and, for authenticated coverage, verifies the required coverage and named digest before lookup or effect. Later references to an authenticated transmitted digest mean this required proof, not an optional substitute. A field-name requirement means the logical HTTP field name, not its bytes or case: `Idempotency-Key` and `idempotency-key` are the same field, and HTTP/2 requires the lowercase form on the wire. Still reject missing, multiple, or malformed logical-field occurrences and any scheme, authority, service-identity, tenant, resource, semantic-header, body, digest, or non-preserving proxy change. Test a mutation of every declared fingerprint input—method, scheme, canonical authority, verified service identity or proxy assertion, intended tenant, normalised resource, each semantic header including `idempotency-key`, and body or digest—and prove rejection before recipient or idempotency lookup, status or outcome retrieval, or effect. Explicitly test shared-proxy authority and route mutations. Also test that an HTTP/2 lowercase `idempotency-key` field is accepted as the one required logical field.

Also pin the expected caller principal and non-secret caller-authorisation binding: authentication scheme, intended tenant, effective scope, key or client-certificate version, and policy generation. Before any token lookup, in-progress or stored-result return, status return, or effect, derive the actual caller principal and binding from end-to-end client authentication and verify equality with the pinned intent and covered fingerprint. If TLS terminates before the recipient, a named trusted proxy identity must supply a separately authenticated, integrity-covered caller assertion that binds those same values; verify it before lookup or effect. A stripped, replaced, or mutated authentication header, mTLS identity, caller assertion, or binding fails closed before any token lookup, result, status, or effect. A later policy generation is acceptable only when the documented retry-equivalence rule maps it to the same pinned binding; it must never create a new effect under the existing token. Test first-attempt stripping or mutation of the authentication header, presented mTLS identity, and trusted-proxy caller assertion, as well as every other declared fingerprint input.

For signed, retried, or externally delivered input, complete the applicable rows. Do not treat an identifier in an unsigned route or header as authenticated merely because another part of the request is signed.

### Order-sensitive external-effect fence

For every order-sensitive external effect, a local per-semantic-effect serialiser is a local scheduling aid only. It cannot fence an HTTP request paused after its local lease check. This rule overrides the table's fence-or-serialiser shorthand. Require either a recipient-visible monotonic source-version fence or a recipient-atomic, irrevocable no-effect tombstone for every older full recipient-observable idempotency composite: verified caller principal, intended tenant, operation, the authorisation binding carried by that older request, and idempotency token. The tombstone irrevocably blocks every future request using that composite. A dispatcher-local attempt generation cannot scope or identify it unless that generation is authenticated on wire and part of the recipient's matching rule. Before the serialiser releases newer work without a passed recipient fence, it must obtain and persist that tombstone. The recipient must reject a stale first send after the tombstone without an effect. An observed `not_applied` result, local CAS, lease expiry, or operator disposition alone is not a tombstone and cannot release newer work. A recipient that supports neither mechanism is ineligible for that effect.

## Decision outcome

When the RFC closes, record whether it was accepted, rejected, withdrawn, postponed, or superseded. Include the rationale, decision date, material dissent, implementation tracking, and the canonical durable follow-up record: a later RFC, ADR, or maintained design record. State exactly what acceptance authorises. For a bounded pilot, record that acceptance authorises only the implementation work needed for that pilot, subject to normal security, change, and release approvals; do not imply production cutover, scale, rollout, or release is complete or authorised. A successful pilot does not authorise a polling reduction when the accepted scope is parallel: require a separate recorded pilot-partner cutover authorisation after final pilot reconciliation. An RFC may link an ADR as context, rationale, or a durable follow-up result, but it cannot replace the ADR or set its normative relationship fields; an ADR needs an Accepted ADR successor.
